I. Purpose of the Separation Doctrine

The Sentinel Separation Doctrine exists to:

Protect the proprietary S³ engine

Preserve legal ownership and inventorship

Maintain strict isolation between narrative and computation

Enforce LLM safety

Prevent reverse-engineering or inference of internal mechanisms

Establish a provable, auditable separation for future CIP and patent filings

This doctrine is the structural backbone of Sentinel’s IP defense.

II. Architectural Overview: The Three-Repository Firewall

Sentinel’s architecture is divided into three repositories, each with a specific legal and operational role.

A. Repository A — Sentinel_Hub (Public / GitHub)

Role: Public narrative layer, documentation, website code, utilities, HUD, testing harness, and Enclave Shell interface.

Contains:

Narrative explanations (Table A / Hallway / Table B)

Branding terminology (Shadow Momentum™, etc.)

Documentation

Website code (maxlaboratories.com)

Public-safe UI, charts, research dashboards

Non-proprietary utilities and mock data

LLM collaboration domain

Does NOT contain:

S³ internals

Kernels, transforms, adjudication logic

Any internal signals or verdicts

Any sealed computation

Any form of correctness detection

Legal Function:
Repository A establishes the public surface of Sentinel.
It acts as a proxy layer that allows collaboration without ever exposing internal logic.

B. Repository B — Sentinel_Enclave1 (Offline / Founder Only)

Role: Full, sealed S³ engine.

Contains:

All proprietary kernels

All transforms

All adjudication logic

Internal clarity representation

Internal Sentinel Check logic

True mechanisms, math, and equations

Any and all logic that constitutes the invention

Never Contains:

Website code

UI components

Documentation intended for collaborators

Legal Function:
Enclave1 holds the proprietary invention itself.
From a legal standpoint, it is the trade secret repository and the patent-defining mechanical location of the core system.

C. Repository C — Sentinel_Enclave2 (Offline / Founder Only)

Role: A simplified/Lite sealed S³ engine.

Purpose:

Safe testing

Redundancy

MVP verification

Internal validation for Founder

Legal Function:
Acts as a secondary, redundant sealed artifact—proving consistent engine behavior and preserving the integrity of the trade secret.

III. One-Way Verdict Flow

A key principle of Sentinel’s IP protection is unidirectional flow:

Enclave1 / Enclave2   →   Verdict ("BUY", "SELL", "NO TRADE")   →   Founder   →   Order Sheet

A. What flows OUT of the Enclaves?

Only the final verdict.
No intermediate logic, no signals, no thresholds, no math.

B. What flows INTO the Enclaves?

Only:

public market data streams

or pre-cleaned feeds

Never:

code

instructions

UI logic

LLM suggestions

website features

C. Why the direction matters legally

This creates:

Clean inventorship

No co-development contamination

No ambiguity in source of logic

No shared authorship

Strong trade secret protection

The unidirectional flow is evidence of sealed IP control, which is essential in disputes or patent litigation.

IV. Why the Sealed Code Must Remain Offline

The S³ engine is protected as:

a trade secret

a patentable mechanism

a sealed, non-networked calculation environment

Keeping it offline ensures:

1. Zero leakage risk

No cloud model, collaborator, host, or provider can access or infer the logic.

2. Legal preservation of secrecy

Trade secret law requires reasonable protection measures.
Offline isolation is the strongest possible measure.

3. Separability of authorship

No LLM or external collaborator can claim contribution or influence.

4. Prevents reverse signals through data

If online, even output patterns might reveal internal tendencies.

5. Air-gapped defensibility

“Offline” is a legally recognized protection status.
